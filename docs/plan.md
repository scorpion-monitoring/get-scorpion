Facts checked on 2026-11-20 for M6b (TeSS `master` at `c48988d`, `tess_rdf_extractors` at TeSS's pinned `88f5401`, Bioschemas specifications at `6c8116e`):

- TeSS's Bioschemas ingestor takes a sitemap (`sitemap*.xml`, `sitemap*.txt`) or a single URL, fetches it raw (no JavaScript), follows up to five redirects itself, and parses content starting with `{` or `[` as JSON-LD. It runs the Event, Course, CourseInstance and LearningResource extractors and deduplicates by `url`, keeping the record with the most fields. An existing event is matched by `url` **within the same content provider** (then by title and start).
- The extractors don't read `eventType`. A Course with a CourseInstance gets the TeSS type "Workshops and courses"; a plain Event gets none (a curator can set it). The "online" flag comes only from `courseMode` (or a VirtualLocation).
- The Event 0.3-DRAFT profile's Minimum properties are `contact`, `description`, `endDate`, `eventType`, `hostInstitution`, `location`, `name`, `startDate`; its four `eventType` terms are listed only in 0.1/0.2-DRAFT (workshops and courses, meetings and conferences, receptions and networking, awards and prizegivings), the same as TeSS's dictionary. Course 1.0-RELEASE requires `description`, `keywords`, `name`; CourseInstance 1.0-RELEASE requires `courseMode`, `location`.
- Hackathons in TeSS are nearly all "workshops and courses" (BioHackathon Germany 2024 to 2026 included; 2023 was "receptions and networking"). Neither schema.org nor Bioschemas has a hackathon type.

## 3. Using the docs export

Recommendation: **read it at build time, but only for the version line and the screenshots.**
Keep the feature text hand-written. The module `displayName`s are internal ("Blob store", "Web shell") and
make poor marketing copy.

- `scorpion-release.json` pins `{ tag, sha256 }` of `docs-export.zip`. GitHub reports no digest for release assets, so this hash is the only integrity check; `pnpm bump-release` computes it from its own download (and compares it with GitHub's digest if one ever appears).
- What the zip holds (v0.16.1, checked 2026-11-20): 65 entries, no directory entries. `docs-export.json` is `{ schemaVersion: 1, scorpionVersion, profiles, files }`; `screenshots.json` is an array of `{ journey, number, slug, light, dark }`; `journeys.json` has the journey titles; further OpenAPI files, `modules.json` and settings schemas, which we ignore. The screenshots are 1280×800 PNGs (50 to 140 KB) for j01 to j10 and j12 (no j11). **Slugs are not unique across journeys** (`account-pending` is in j01 and j02), so the mapping keys on journey plus slug.
- `scripts/fetch-docs-export.mjs` runs before `astro build` and `astro dev` (`pnpm build`, `pnpm dev`). It downloads the zip over https without a token (limit 20 MB), checks the sha256 **before** opening it, and caches the verified zip in `node_modules/.cache/get-scorpion/` by hash, so a second build doesn't download it again. It opens the zip with yauzl as untrusted data: it rejects names with `..`, a leading `/`, a drive letter, a backslash or unexpected characters, duplicate names, symlinks and other non-regular files, encrypted entries and unknown compression, and limits the entry count (1,000), each entry (10 MB) and the declared total (100 MB). It reads only `docs-export.json`, `screenshots.json` and the mapped pairs, checks that `schemaVersion` is 1 and `scorpionVersion` equals the tag, checks the PNG headers, clears `src/assets/generated/` and writes the files under paths built from our own validated data.
- `src/data/screenshots.yaml` maps a feature card id to `{ journey, slug, alt }` (`alt` is a message key). The fetch script fails the build when a pair is missing from `screenshots.json`, so a rename upstream is noticed.
- **`pnpm check` doesn't fetch.** CI runs `check` before `build`, so nothing that `astro check` type-checks imports a generated file: `src/lib/generated.ts` reads them through `import.meta.glob`, which is empty on a fresh clone. Rendering without them fails with a message that names the fetch command.
- The same script downloads the two OpenSSF badges (§6, §12.10).
- **Bumping:** `pnpm bump-release` rewrites `scorpion-release.json` to the latest release. The scheduled workflow (weekly, plus `workflow_dispatch`) that opens the bump PR is deferred to M7: a PR opened with `GITHUB_TOKEN` doesn't trigger `ci.yml`, so the required checks would never run, and it would need "Allow GitHub Actions to create and approve pull requests". M7 uses a GitHub App token or similar. Until then the version line shows the pinned release, which lags behind the newest one by up to a week (longer if nobody bumps).
- Nothing is fetched at runtime.

## 4. Events feed (no restart)

- **Source of truth:** one YAML file per event in `events/` in this repo, `events/<id>.yaml`, copied from `events/_template.yaml` (files starting with `_` are skipped). Required fields: `id, type, start, end, title{en,de}, summary{en,de}, location, host{name, url?, ror?}, contact{name, email?, url?}` (contact with an email or a URL), plus `mode` and `keywords` for `type: training` (`mode` is not allowed for other types). Optional: `url`, `registration` (both https only), `address{venue?, street?, postalCode?, locality, country}`, `keywords`, `capacity`, `language`, `tess`. No other fields (decisions in §1, M5 and M6b). Limits: id 64, title 120, summary 400, location, names and address parts 120, URLs 500, email 254 characters; 1 to 10 keywords of at most 40 characters without commas, unique ignoring case; capacity 1 to 100,000; `country` ISO 3166-1 alpha-2, `language` ISO 639-1. The email must not contain `? # & % /`, so the page's `mailto:` link can't carry extra headers.
- **Contract:** `events/events.schema.json` (JSON Schema draft 2020-12) holds two schemas: the root (`#/$defs/event`) is one event file, `#/$defs/feed` is `events.json` (`{ schemaVersion: 1, events: [...] }`), which the M8 host timer checks too. What a schema can't express is checked in code: real calendar dates of the same kind, `end` not before `start`, the id equals the file name and is unique, every URL parses as https without user name or password, keywords are unique ignoring case.
- **Compatibility (M6b):** clients reject an entry with any field they don't know (the shape check repeats the schema exactly), and `events.yml` publishes a new feed as soon as a change reaches `main`, while the client ships with the image (M8). So within `schemaVersion` 1 a field is only ever **added as optional**, together with the client that knows it, and **no event file uses it until that image is deployed**. Anything else (a new required field, a removed or renamed field, a changed meaning) bumps `schemaVersion`, and the release then carries the old and the new feed side by side (for example `events.json` and `events.v2.json`) until every deployed client reads the new one. M6b changed the format in place because no client read the feed in production yet.
- **Shared rules:** `src/lib/events.ts` holds the date rules (Europe/Berlin day boundaries, including DST), "past", the sort order, the event's URL (`eventUrl()`: `url`, or `https://scorpion.bi.denbi.de/#event-<id>`) and a shape check that repeats the schema for the browser. It imports nothing, so `scripts/build-events.mjs` imports it directly (Node 26 strips the types) and Vite bundles it into the client script. `build-events.mjs` fails if its `LIMITS`, `EVENT_TYPES` or `MODES` differ from the schema, and a unit test checks that the shape check rejects every case the schema rejects.
- **TeSS markup (M6b):** `src/lib/event-jsonld.ts` builds, from validated events and in English, one node per event: a schema.org `Event` (Bioschemas Event 0.3-DRAFT, the only version) with `eventType` as a `DefinedTerm` of the profile's vocabulary, or for `training` a `Course` (Course 1.0-RELEASE) with one nested `CourseInstance` (CourseInstance 1.0-RELEASE). Each node has `dct:conformsTo` its profile and a stable `@id` on our site (`#event-<id>`; the Course `#course-<id>`); `url` is `eventUrl()`, which TeSS deduplicates by. `location` is a Place with a PostalAddress when `address` is given, otherwise the `location` text. Host → `hostInstitution` and `organizer` (and `provider` of a Course), contact → `contact`, registration → `offers` (an Offer with its URL), capacity → `maximumAttendeeCapacity`, language → `inLanguage`, keywords → comma-separated `keywords` (Course: Minimum). Beyond the profiles, for TeSS: `organizer` and `inLanguage` on an Event, `hostInstitution` and `contact` on a CourseInstance. `scripts/lib/event-profiles.mjs` checks each node offline with M6's `checkNode()` against the vendored profile schemas (`scripts/bioschemas/`, source, hash and licence in its README), plus the document rules (only `@context` and `@graph`, unique `@id` and `url`, a known `eventType`). The generated schemas need two adaptations, both documented there: `oneOf` is read as `anyOf` (their object definitions don't constrain `@type`, so a Place matches several branches), and the `date` format accepts date-times (they model DateTime as an object).
- **`events.jsonld` (M6b):** `{ "@context": …, "@graph": [ … ] }` with a node per upcoming event that doesn't have `tess: false`, in feed order, serialised by `serializeJsonLd()` (indented, every `<` escaped). It starts with `{`, so TeSS reads it as JSON-LD. With no such events it is a valid document with an empty `@graph`.
- **Build:** `pnpm events:check` validates (in CI's `build` job); `pnpm events:build` also writes the feed, past events dropped and sorted, to the git-ignored `.cache/events/events.json` (or `--out <file>`) and `events.jsonld` next to it (or `--out-jsonld <file>`), and fails if either doesn't validate; `--check-feed <file>` and `--check-jsonld <file>` validate a published file. YAML is parsed with the `yaml` package (core schema, unique keys, no custom tags or aliases). `pnpm test` runs `node --test` on `scripts/build-events.test.mjs` with fixtures in `scripts/fixtures/events/` (one event of each type, one past, one without `url`, one with `tess: false`).
- **TeSS check (M6b, by hand):** the fixture's `events.jsonld` was run through `tess_rdf_extractors` at TeSS's pinned revision (Ruby 3.4.13 and TeSS's RDF gem versions, in a throwaway container, offline). It extracted every node: four Events and one Course, whose CourseInstance merges into the same record because both share the `url`. Fields filled: title, description, url, start, end, venue, city, postcode, country, organizer, host institutions, contact (name and email), capacity, keywords, language; for a training also the type "Workshops and courses" and "online" (true only for `mode: online`). Not read by TeSS: `eventType`, the contact's URL, `offers`. This check is not in CI (it needs Ruby); repeat it when the markup changes.
- **Publish:** `.github/workflows/events.yml` runs on a push to `main` that touches `events/`, `scripts/build-events.mjs`, the event and JSON-LD code (`src/lib/events.ts`, `event-jsonld.ts`, `jsonld.ts`, `scripts/lib/bioschemas.mjs`, `event-profiles.mjs`, `scripts/bioschemas/`) or the workflow, daily at 03:17 UTC, and on `workflow_dispatch`. Job `build` (read-only) validates and builds `events.json` and `events.jsonld`; job `publish` (the only one with `contents: write`, no checkout, no dependencies) creates the `events` pre-release if missing and uploads both files with `--clobber`; job `verify` (read-only) downloads both from `https://github.com/scorpion-monitoring/get-scorpion/releases/download/events/` without a token, compares them byte for byte with the built files and validates them. Runs queue (`cancel-in-progress: false`), so the last one wins. GitHub disables scheduled workflows after 60 days without repository activity; the push trigger still works then.
- **Cached 404 (found after the M5 merge):** right after the first upload, an anonymous request from one network got a cached 404 for a few minutes, while the runner and token-authenticated requests got the file. A fetcher must therefore treat a 404 or an invalid file as "keep the last good file", never as "no events".
- **Deliver (M8):** the image serves `/events/` from a **mounted volume**. A small timer on the host fetches **both assets**, `events.json` and `events.jsonld`, every 15 minutes, checks each (`events.json` parses and matches `#/$defs/feed`; `events.jsonld` passes `--check-jsonld`, or at least parses and starts with `{`), and replaces each file atomically and independently; on a 404, a network error or an invalid file it keeps the last good file (see the cached 404 above). nginx serves the new files on the next request, with no restart. Visitors' browsers only ever request our own origin. The alternative is a sidecar container in place of the host timer, depending on how the host is run (open point). **Until M8 is deployed, the release is published but not served**; TeSS reads `events.jsonld` from the release URL meanwhile.
- **Fallback:** `public/events/events.json` is an empty feed (`{ "schemaVersion": 1, "events": [] }`) and `public/events/events.jsonld` an empty document (`@graph: []`), so the section stays hidden and the `alternate` link resolves if the mount is missing. `check-dist.mjs` checks that both are valid and empty.
- **Render:** `src/components/Events.astro` renders the section with `hidden`, its `<h2>`, an empty list, the pager and a `<template>` for one event; every visible string comes from `messages/` (the type labels in `data-type-<type>` attributes), and the pager status is a message with `{page}` and `{pages}` left in a `data-` attribute. The client script `src/scripts/events.ts` (7.3 KB minified since M6b, 4.8 KB in M5, because of the longer shape check) fetches `/events/events.json` with `cache: 'no-cache'`, treats it as untrusted, drops invalid, past and non-https entries, formats dates with `Intl.DateTimeFormat` in `<html lang>` (dates as calendar days, date-times in Europe/Berlin), fills copies of the template with `textContent` only (links get validated https URLs or a `mailto:` of a validated address), and then removes `hidden`. Each card shows title, type label, date, location, contact (name, linked to its URL if given, and the email), summary, "Event details" if `url` is set and "Register" if `registration` is set. Each `<li>` gets `id="event-<id>"`; when the page's fragment names an upcoming event (on load or on `hashchange`), the script shows the pager page that holds it, scrolls its `<h3>` (`tabindex="-1"`) into view and focuses it; an unknown or past id changes nothing. Any failure (network, 404, JSON, template) leaves the section hidden and logs nothing. Without JavaScript the section stays hidden. This is the page's only JavaScript.
- **External, not inline (found in M5):** Astro inlines a processed `<script>` that imports nothing and is smaller than `build.assetsInlineLimit` (4 KB by default; `astro/dist/core/build/plugins/plugin-scripts.js`), and an inline script would be blocked by `script-src 'self'`. `astro.config.mjs` sets `vite.build.assetsInlineLimit` to a function that returns `false` for `.js` files (and leaves the default for other assets). Checked by building with a limit of 10 KB: without the function the script was inlined, with it the page has one `<script type="module" src="/_astro/….js">`. The script stays a processed, bundled and hashed TypeScript file rather than a hand-written file in `public/`, so it is type-checked, can share `src/lib/events.ts`, and gets an immutable cache lifetime (§9).

- i18n: Astro's built-in i18n routing combined with **Paraglide JS 3** for strings (maintained, compile-time, no runtime loader). Checked in M2 (§12.9), with these findings:
  - Paraglide 3.0 came out on 2026-11-03, and the 2.x line had its last release on 2026-10-28, so we use 3.x. The 3.0 breaking changes (`additionalFiles` and middleware locale splitting removed, Vite output as virtual modules) don't affect a static page.
  - No adapter package: `@inlang/paraglide-astro` is deprecated on npm. The Vite plugin from `@inlang/paraglide-js` goes into `astro.config.mjs` under `vite.plugins`.
  - Each page passes its locale to every message call (`m.key({}, { locale })`). This needs no locale strategy, no `setLocale()` and no Astro middleware, and it works with `prefixDefaultLocale: false`. (Paraglide's own SSG guide assumes a prefix for every locale and a middleware.)
  - `paraglide-js init` points `project.inlang/settings.json` at plugin modules on jsDelivr, which would fetch unpinned code at every build. Instead `@inlang/plugin-message-format` is a dev dependency, pinned by the lockfile, and `modules` names its file in `node_modules`. Module paths resolve from the repository root, not from `project.inlang/`. A wrong path is only a warning, but then every message is missing and `pnpm check` fails.
  - A key missing from one locale's file falls back to English without a warning. Since M3, `scripts/check-messages.mjs` fails when `en.json` and `de.json` don't have the same keys; `pnpm check` runs it before `astro check`, so CI runs it in the `build` job.
  - The output has no inline `<script>`, `<style>` or `style=""`. Until M4 the built HTML had no script at all; since M5 it has exactly one external module script, the events script (§4). There is only one stylesheet. The page never redirects automatically by `Accept-Language`. It sets `<html lang>`, `hreflang` alternates and a visible EN/DE switcher.
- Commands: `pnpm install`, `pnpm dev` and `pnpm build` (both run `fetch-docs-export` first, so they need network access to GitHub unless the zip is cached), `pnpm bump-release`, `pnpm preview`, `pnpm lint`, `pnpm check`, and `docker compose up` to preview the real nginx config. Node LTS is pinned in `.nvmrc` and `engines.node` (Node 26, LTS since 2026-10-28), pnpm in `packageManager` (pnpm 12). The application repo is still on Node 24 and pnpm 10; the two need not move together.
- Node 25 and later no longer ship Corepack. Locally, run `npm install --global corepack` once before `corepack enable`. CI uses `pnpm/action-setup` and isn't affected.
- pnpm 12 fails `pnpm install` when a dependency has a build script that isn't allowed (`ERR_PNPM_IGNORED_BUILDS`). In M2 no dependency has one, so there is no `allowBuilds` list and no `pnpm-workspace.yaml`. Astro 7 builds with Vite 8 and rolldown, so esbuild isn't in the tree, and sharp 0.35 installs prebuilt binaries without a script. Add a package to `allowBuilds` in `pnpm-workspace.yaml` only when an install fails this way.
- pnpm 12 also enforces a minimum release age by default. It rejected an Astro patch released the day before, and `pnpm add` then wrote an exclusion into `pnpm-workspace.yaml` by itself. Don't commit such exclusions; pick the previous version instead.
- Data files (found in M3): each `src/data/*.yaml` is a map from entry id to fields, loaded with Astro's `file()` loader. On its own, `file()` only logs an error when the file is missing or isn't valid YAML, and keeps the entries cached from the last build, so `src/content.config.ts` wraps it to fail the build instead. Schema errors (unknown fields, non-`https:` URLs, unknown message keys) fail `pnpm check` and `pnpm build`; a logo path that doesn't exist fails only `pnpm build`. Visible text stays in `messages/`: the YAML holds message keys, apart from organisation names.
- Dependencies added in M4: `yauzl` 3.4.0 (MIT; one dependency, `pend`; no build script) to read the zip, chosen over the dependency-free `fflate` because it validates file names and entry sizes and exposes the external attributes needed to reject symlinks; `yaml` 2.9.1 (ISC; no dependencies; already in the tree through Astro) so the fetch script can read `screenshots.yaml`.
- Dependency added in M5: `ajv` 8.20.0 (MIT; dependencies `fast-deep-equal`, `fast-uri`, `json-schema-traverse`, `require-from-string`; no install script; already in the tree through ESLint, so the lockfile only gains the direct entry). Tests use Node's built-in `node --test`, so there is no test framework.
- Dependencies added in M6: `opentype.js` 2.0.0 (MIT; no dependencies, no install script) for the Open Graph text, and `sharp` 0.35.5 (Apache-2.0) as a direct dev dependency, the version Astro already uses (pnpm doesn't hoist it, so the script can't import it otherwise). The Inter 4.1 font (OFL-1.1) is downloaded by `pnpm og-images`, checked against a pinned sha256 and cached in `node_modules/.cache/get-scorpion/`; it is not committed and never served. opentype.js 2.0 can't apply Inter's `ccmp` lookups (GSUB type 6, format 2), so the script lays glyphs out itself (character map and pair kerning).

## 6. Theme, assets, accessibility, privacy

- **Theme:** copy the two `@plugin 'daisyui/theme'` blocks verbatim into `src/styles/app.css`, with a header comment naming the source file and commit (`490d48d`). Copying keeps builds reproducible. `scripts/check-theme-drift.mjs` runs weekly and opens an issue if the upstream tokens change. The page follows the system theme only: no toggle and no storage.
- **Logos:** use SVG wherever possible. Scorpion's own logo has no SVG upstream: it is the light and dark PNG wordmark ("Powered By Scorpion") from `apps/web/src/lib/assets/` at `490d48d`, optimised to WebP by `astro:assets` (the 2× variant is capped at the 128 px source height). Until permission is recorded, organisation logos render as a neutral placeholder (the name in a dashed box at the logo's size, with the final alt text); swapping in a file is a YAML change (`logo.src`, `logo.dark`). Each logo needs written permission or a published brand policy (de.NBI, ELIXIR-DE, NFDI4Biodiversity, NFDI4Microbiota, IPK, DFG). This is recorded in `ASSETS.md` with source URL, date and terms. Where a logo fails contrast on dark, ship a dark variant through `<picture><source media="(prefers-color-scheme: dark)">`.
- **Images:** screenshots go through `astro:assets` (sharp) as AVIF or WebP with fixed `width` and `height` and lazy loading. The light and dark screenshot pairs use the same `<picture>` media switch.
- **Badges:** the fetch script downloads the OpenSSF badge SVGs at build time (Best Practices from bestpractices.dev; Scorecard from api.scorecard.dev, which redirects to img.shields.io). Hotlinking them would make a third-party request at runtime. They are treated as untrusted: https only, content type `image/svg+xml`, at most 16 KB, no script, style, foreignObject, event handlers, external references or `data:` URLs, and the value (level, score) must parse from the `aria-label`. They are served as `<img>` files from our origin, never inlined; the alt text is built from our own messages and the parsed value.
- **The one inline block (M6):** the built pages carry no inline script, with one exception: the landing pages have exactly one `<script type="application/ld+json">` with the structured data (§7). It is a data block, not a script: browsers never execute that type, so `script-src 'self'` doesn't block it and it causes no CSP violation (checked in Chromium with the CSP below), and crawlers read JSON-LD only inline. Rules: no other inline script; never an executable type; the JSON is serialised with every `<` written as `\u003c` (`serializeJsonLd()` in `src/lib/jsonld.ts`), so no data can end the element. `scripts/check-dist.mjs` enforces this on every build. M6b adds **no** exception: the event markup is the separate file `/events/events.jsonld`, linked with `<link rel="alternate" type="application/ld+json">`, and the events script doesn't write markup into the page (decided in §1).
- **No third-party requests:** system fonts, no analytics, no CDN. A strict CSP is set in `nginx.conf`: `default-src 'self'; img-src 'self' data:; style-src 'self'; script-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'none'`. Astro's `build.inlineStylesheets: 'never'` keeps `style-src` strict. Further headers: HSTS (if the proxy doesn't set it), `X-Content-Type-Options`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Permissions-Policy`.
- **WCAG 2.2 AA:** the theme tokens are already AA-tuned for text (light). Contrast is checked in **both** themes and both locales in CI (§8). All logos have meaningful alt text ("de.NBI / ELIXIR-DE logo"), screenshots have descriptive alt text, and decorative icons have `aria-hidden`. Other requirements: a skip link, visible `:focus-visible` rings with daisyUI's focus colour, logical heading order (one `h1`), and target size of at least 24×24 px. External links in the same tab, with the destination clear from the link text.
- **Mobile:** the layout is checked at 320, 375, 768 and 1280 px. The nav collapses to a `<details>` menu, which needs no JavaScript.

## 9. Deployment

- `docker/Dockerfile` is multi-stage: `node:<lts>-alpine@sha256:…` builds, then `nginxinc/nginx-unprivileged:<ver>-alpine@sha256:…` serves. The container runs as a non-root user on port 8080 with a read-only root filesystem and `/events/` as a volume. It has a `/healthz` endpoint.
- `nginx.conf` sets the headers from §6. Hashed assets get `Cache-Control: immutable` for a year, HTML and `/events/` get `no-cache`, and there is a custom 404. `/events/events.jsonld` is served as `application/ld+json` (nginx's default `mime.types` doesn't know `.jsonld`), `/events/events.json` as `application/json`; TeSS fetches the former server-side, so it needs no CORS header. The container only serves `/`, `/de/`, `/robots.txt`, `/sitemap.xml` and assets. Routing `/denbi/` and `/nfdi/` stays with the reverse proxy.
- Host timer (§4): fetches `events.json` and `events.jsonld` from the `events` release into the `/events/` volume, each checked and replaced atomically, keeping the last good file on a 404 or an invalid download. After the cutover, the TeSS source may move to `https://scorpion.bi.denbi.de/events/events.jsonld` (CONTRIBUTING.md).
- Rollout: the operator pulls the new tag (or Watchtower/Renovate on the host does). The exact step depends on the open point below.
